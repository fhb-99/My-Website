博客是怎么真正跑起来的？

从用户打开首页，到读取文章、加载封面、上报阅读量，再到管理员导入 Markdown、保存草稿并发布——这份文档按当前代码，把每一步经过的前端、Nginx、PocketBase、SQLite 与文件存储完整串起来。

当前主路径：Vue 3 + PocketBase 生产入口：https://gentleyun.cn 数据：SQLite + pb_data 文件 更新日期：2026-09-29

先说结论

这个博客不是“每篇文章对应一个 HTML 文件”，也不是当前仍由 C++ 服务直接输出页面。它是一个前后端分离、同域部署的动态内容站点。

用户浏览器→ Nginx / HTTPS→ Vue 用户端或管理端→ PocketBase REST API→ SQLite / 上传文件
前端

负责“看起来怎样、如何交互”

路由、页面、搜索条件、加载状态、Markdown 渲染、目录滚动、主题与本地收藏，都在浏览器里完成。

后端

负责“数据是否允许读写”

PocketBase 提供 REST 接口、管理员认证、集合规则、数据校验、SQLite 持久化和文件服务。

内容

文章存数据库，不跟页面打包

发布文章时写入 posts 记录；用户下一次请求即可读取，无需为每篇文章重新构建 Vue。

必须区分现行架构与历史代码 Back-end-server/backend-cpp 是旧 C++/SQLite 实现，不是当前生产主路径。用户端仍保留“未配置 PocketBase 时回退旧 API”的迁移兼容代码，但生产部署应明确配置 VITE_POCKETBASE_URL，不能把回退路径当成现状。

02生产环境怎么运行

用户只看到一个域名，但 Nginx 会根据 URL 将请求送到完全不同的位置。

静态内容

/ 与 /admin/

Nginx 直接从磁盘返回构建后的 HTML、JavaScript、CSS。用户端位于站点根目录，管理端位于 /admin/ 子目录。

动态接口

/api/

Nginx 不自己处理文章数据，而是把请求转发给只监听 127.0.0.1:8080 的 PocketBase。

公网浏览器 └─ https://gentleyun.cn └─ Nginx :443 ├─ / → /var/www/gentleyun/html/ （用户端静态文件） ├─ /admin/ → /var/www/gentleyun/html/admin/ （管理端静态文件） ├─ /api/* → 127.0.0.1:8080 （PocketBase） └─ /_/ → 404 （屏蔽原生管理后台） PocketBase systemd 服务 └─ /opt/gentleyun-blog/pocketbase serve ├─ --dir=/opt/gentleyun-blog/pb_data ├─ --hooksDir=/opt/gentleyun-blog/pb_hooks └─ --migrationsDir=/opt/gentleyun-blog/pb_migrations
“同域部署”带来的结果 前端页面与 API 都使用 https://gentleyun.cn，浏览器访问 /api/... 时不需要跨域跳到另一个公网域名；PocketBase 也没有直接暴露在公网端口上。

Nginx 还承担 HTTP→HTTPS 跳转、上传体积上限、登录限流和写请求限流。PocketBase 服务由 systemd 守护，异常退出后可自动拉起。生产博客不能占用服务器的 8090，该端口已有其他服务；生产 PocketBase 使用本机 8080。

03用户浏览内容时，完整链路是什么

下面先看一次最典型的“打开文章列表”。页面壳与文章数据其实是两轮不同的网络请求。

第一轮：下载前端程序

浏览器请求首页

GET https://gentleyun.cn/ 到达 Nginx。

Nginx 返回静态文件

返回用户端构建后的 index.html，浏览器再下载 JS 和 CSS；这一步还没有取文章正文。

Vue 在浏览器中启动

Vue Router 使用 Hash 路由，例如 #/posts、#/posts/记录ID；Pinia 初始化主题、音乐等状态。

第二轮：按页面需要请求数据

组件调用前端 API 封装

文章列表页调用 postsApi.listPosts，带上页码、关键词、标签和内容类型。

浏览器发起 PocketBase 请求

例如 GET /api/collections/posts/records?page=1&perPage=10&filter=...。

Nginx 反向代理

匹配 /api/ 后转给 127.0.0.1:8080，请求路径保持不变。

PocketBase 执行公开读取规则

未登录用户只能读取 is_published=true 的文章；草稿在服务端就被过滤，而不是仅由前端隐藏。

查询 SQLite 并返回 JSON

记录与展开的标签通过 Nginx 返回浏览器；前端将 PocketBase 字段映射为共享 TypeScript 类型。

Vue 渲染页面状态

数据到达后显示卡片；无记录显示空状态；失败显示错误和重试入口，不使用伪造占位文章。

打开一篇文章详情时又发生什么

  1. 路由进入 #/posts/:id，详情组件调用 postsApi.getPostDetail(id)。
  2. 接口先按记录 ID 查询；为了兼容旧链接，也会尝试 slug 或历史 ID。无论哪种方式，公开规则都要求文章已发布。
  3. 记录如果已有可信的 content_html 就使用它；否则在浏览器中用 MarkdownIt 将 content_md 转为 HTML。
  4. 转换后的 HTML 再经过 DOMPurify 清洗，降低文章内容注入危险标签或脚本的风险。
  5. 文章目录由浏览器扫描正文中的 h2/h3/h4 生成；目录点击、代码复制、滚动高亮等不需要后端参与。
  6. 页面还会分别查询上一篇、下一篇与已审核评论，然后更新对应区域。
为什么网址带 #？ 两端都使用 createWebHashHistory()。# 后的路径由浏览器中的 Vue Router 处理，不会作为服务器路径发送；因此刷新 https://gentleyun.cn/#/posts/abc 时，Nginx 仍然只需返回根目录的 index.html。

阅读量为什么不是一打开就加一

文章停留约 10 秒→ POST /api/posts/{id}/view→ Hook 开启事务→ 检查“文章 + 访客 + UTC 日期”→ 首次则事件入库并 +1

前端会在 LocalStorage 保存一个随机访客 ID。后端 Hook 在事务内查询 post_view_events；当天已经存在同组合记录时返回“未计数”，不存在时才插入事件并原子递增 posts.views。因此它表示“同一浏览器访客每天一次”的近似阅读量，而不是登录用户的精确人数。

封面图片、音频等文件怎么显示

文章列表 JSON 不会把图片二进制塞进正文响应。数据库记录只保存 PocketBase 文件名；前端拼出文件 URL 后，浏览器再单独请求：

GET /api/files/{collectionId}/{recordId}/{filename}

该请求同样经过 Nginx → PocketBase，PocketBase 再从 pb_data 中读取对应文件并返回。于是一次文章列表页面可能产生：1 次列表 JSON 请求 + 多次封面图片请求。音乐文件也是同一机制，只是所属集合与字段不同。

04用户评论、留言等写操作如何到后端

公开用户不是完全只读，但所有可写入口都受后端集合规则约束。

评论

详情页提交昵称与内容，前端固定发送 status: pending，并关联当前文章。

POST /api/collections/comments/records

→

PocketBase

创建规则再次校验状态必须为待审核，写入 SQLite。只有管理员改成 approved 后，公开列表规则才会让它出现。

留言板使用相同思路：公开创建 guestbook_messages 的待审核记录，管理员在管理端通过或拒绝。前端表单的限制能改善体验，真正的安全边界仍是 PocketBase 规则，因为攻击者可以绕过网页直接调用 API。

当前“邮箱验证”不是账号系统 访客昵称、邮箱门槛等信息主要保存在当前浏览器 LocalStorage；评论/留言提交给 PocketBase 的核心字段是昵称、内容、状态及必要关联。它不能被描述成已注册账号、云端身份或跨设备同步。

05从后台上传文章到用户看见：完整链路

“上传一篇文章”实际包含管理员认证、正文写库、可选文件上传和发布状态控制。发布后不会生成独立 HTML 文件。

第一段：管理员进入后台并登录

打开 https://gentleyun.cn/admin/

Nginx 返回管理端 Vue 构建产物；后台与用户端是两套独立前端。

提交管理员账号与密码

管理端调用 POST /api/collections/_superusers/auth-with-password；该精确路径在 Nginx 层有单独登录限流。

PocketBase 验证并返回 Token

管理端把 Token 与管理员邮箱保存在 LocalStorage；后续管理请求携带 Authorization 头。

路由守卫允许进入管理页

前端守卫主要检查 Token 是否存在；Token 是否真实、是否过期最终由 PocketBase 在每个写请求上判断。

第二段：新建或编辑文章

表单收集文章数据

标题、slug、摘要、Markdown 正文、标签、文章类型、是否发布，以及可选封面。前端先检查必填项。

解析标签

管理端先查询标签集合；不存在的标签会创建，最后得到 PocketBase 关系字段需要的标签记录 ID。

正文写入 posts 集合

新文章使用 POST /api/collections/posts/records，编辑使用 PATCH /api/collections/posts/records/{id}。正文写入 content_md，保存时清空旧 content_html，避免与新 Markdown 不一致。

PocketBase 校验并写 SQLite

验证唯一 slug、字段类型、标签关系和管理员权限。新文章阅读量从 0 开始。

有封面时再发 multipart 请求

浏览器把图片作为 FormData 对同一记录执行第二次 PATCH；PocketBase 将文件写入 pb_data，记录只保存文件名。

管理端重新拉取记录

接口展开标签关系并刷新列表，让管理员看到后端最终保存结果。

第三段：草稿与发布如何影响用户端

草稿

is_published = false

记录已经存在 SQLite，管理员能读取和继续编辑；公开 list/view 规则会将它挡在服务端，用户无法通过猜 URL 看到。

已发布

is_published = true

下一次用户端列表或详情 API 请求即可返回这条记录。Vue 前端无需重新构建，也不会生成新的文章 HTML 文件。

一句话理解发布 发布文章 = 把一条通过校验的 posts 数据记录设为公开可读；它是数据状态变化，不是重新部署网站。

后台“导入 Markdown”到底上传了什么

当前 Markdown 导入是浏览器端导入，不是把原始 .md 文件直接存到服务器：

  1. 管理员选择本机 .md 文件。
  2. 浏览器通过 File.text() 读取文本；第一行一级标题可作为标题，否则用文件名。
  3. 前端生成摘要与 slug，把文本放进 content_md。
  4. 创建一条 未发布草稿 记录；原始 .md 文件本身不会作为附件保存在 PocketBase。
  5. 管理员进入文章管理补充标签、封面、摘要并发布。

因此，如果原 Markdown 引用本机相对图片路径，线上不会自动拥有这些图片；图片需要变成可访问的线上资源，或通过相应的文件上传流程处理。封面上传与 Markdown 正文导入是两条独立链路。

“高性价比人生指南”与普通文章的区别

指南采用 guides（整本指南元数据）和 guide_chapters（章节）两级数据，用户端用左侧目录切换章节。批量导入脚本会读取指定目录中的多份 Markdown，按章节号与 slug 写入 PocketBase；它不是普通文章表单的另一种显示方式。两者共用 PocketBase 与 Markdown 安全渲染思路，但数据模型和页面路由不同。

08权限与安全边界

真正可信的限制必须在请求抵达后端后仍然成立。

可信边界

PocketBase 访问规则

  • 未发布文章、随记、项目和指南不能公开读取。
  • 评论与留言只能公开创建为待审核状态。
  • 管理写操作需要有效超级管理员身份。
  • 字段类型、文件 MIME、大小和关系由集合定义校验。
外围保护

Nginx 与前端安全处理

  • HTTPS、同源 API、登录/写请求限流。
  • 公网屏蔽 PocketBase 原生 /_/ 管理界面。
  • Markdown 转 HTML 后使用 DOMPurify 清洗。
  • 不把账号、Token、密钥或生产数据提交进仓库。

哪些东西不能只依赖前端

  • “按钮不显示”不是权限。攻击者可以自己构造 HTTP 请求，所以后端仍需验证 Token 与规则。
  • 路由守卫不是会话真相。LocalStorage 中有 Token 只能说明曾经登录；失效 Token 会被后端拒绝。
  • 前端表单校验不是数据校验。后端必须继续约束必填、唯一值、状态和关系。
  • 浏览器访客 ID 不是身份证明。它可被清理或更换，只适合做阅读量的轻量去重。

当前 PocketBase 路径仍保持人工审核语义；历史 C++ 配置中的 AI 审核不等于现行生产已具备自动审核。

数据本地 pb_data，可抛弃测试数据生产 /opt/gentleyun-blog/pb_data，必须备份
VITE_* 是构建时变量 它会在 npm run build 时写进前端产物，不是服务器运行后随便改环境变量就能生效。地址改动后需要重新构建并部署对应前端。

本地若没有配置 VITE_POCKETBASE_URL，用户端可能走历史 C++ API 回退。页面能打开不代表验证了当前 PocketBase 生产链路；调试现行架构时必须显式配置该变量并启动本地 PocketBase。

10改什么，需要重新发布什么

理解这张表，可以避免“只上传文章却重启服务”或“改了前端源码却只改数据库”这类混乱。

变更需要做什么通常不需要什么
新增/编辑/发布文章通过管理端或受控脚本写 PocketBase 数据不需要重新构建前端，不需要重启 Nginx
更换文章封面上传文件并更新对应记录不需要把图片手工复制到前端 assets
修改用户端页面样式/交互用户端 typecheck/test/build，替换用户端静态产物通常不需要改 SQLite
修改管理端表单/UI管理端 typecheck/build，替换 /admin/ 静态产物字段未变时不需要迁移
新增集合或字段新增可重复、可回滚迁移；同步类型、API 与页面；部署迁移不能手工改生产库代替迁移
修改阅读量 Hook部署 Hook、按流程重启/验证 PocketBase不一定需要重建前端，除非接口契约也变
修改 Nginx 路由/限流备份配置、nginx -t、平滑重载和健康检查不需要修改文章数据

11最容易产生的几个误解

误解 1：每篇文章都是一个网页文件

实际：Vue 是统一页面壳，文章是数据库记录；详情页根据路由参数动态请求并渲染。

误解 2：发布文章要重新部署网站

实际：只要数据模型未变，发布只是更新 is_published；用户下一次请求就能读到。

误解 3：前端不显示草稿就安全了

实际：安全来自 PocketBase list/view 规则。前端只是交互层，不能阻止直接 API 请求。

误解 4：导入 Markdown 就保存了原文件

实际：浏览器读出文本后写入 content_md，原始文件没有作为附件上传。

误解 5：收藏、邮箱都是后端账号数据

实际：当前主要是 LocalStorage 状态，清理浏览器或换设备不会自动同步。

误解 6：仓库里的 C++ 就是线上后端

实际：C++ 目录是历史实现。现行主路径是 PocketBase、迁移、Hook 与两个 Vue 前端。

误解 7：只备份 SQLite 就够了

实际：还必须保留上传文件；生产备份的对象应是完整、相互一致的 pb_data。

误解 8：Vue 页面访问数据库

实际：浏览器只访问 HTTP API；SQLite 不对浏览器开放，读写由 PocketBase 执行。
